# 阿里云权限与数据库权限

Status: ready-for-agent

术语以仓库根目录 `GLOSSARY.md` 为准。本规格里的「决策 N」指 `docs/product-design.md` §10 的历史决策。

## Problem Statement

**阿里云**：成员要用 `aliyun`、`ossutil` 直接操作团队的阿里云资源时，只能找管理员在 RAM 控制台手工建用户、发 AccessKey、绑策略。这个过程没有申请记录，没有审批，也没有统一的地方能看到「谁持有什么权限」。有人离职或转岗，管理员要靠记忆逐个云账号去收回。团队还接入了不止一个云账号，情况更乱。另一方面，EAT 现有的 OSS 空间给每人建了一个 OSS 专用的 RAM 身份。如果再按人发阿里云权限，同一个人在同一个云账号里就会有两个 RAM 用户、两把 Key。

**数据库**：成员要访问团队已有的数据库时，可选的路子都不对：
- 要么拿分配出去的 owner 账号密码。这个账号权限过大、多人共用，没法只收回其中一个人。
- 要么找 DBA 手工建号。没有审批，也没有记录。
- 外部库（不是 EAT 建的库）在 EAT 里根本没有入口。

**凭证落盘**：AI Agent 代成员操作时，经常把数据库密码或 Key 写进 `.env` 或者 shell 历史里。

**停用不彻底**：停用一个 EAT 用户后，他在数据库上的访问不受任何影响。

## Solution

EAT 新增两项可申请、可审批、可撤销的权限，并把它们放进现有的统一申请中心：

- **阿里云权限**：
  - 管理员在系统设置里接入一个或多个云账号。EAT 自动发现每个云账号里以 `eat-perm-` 开头的自定义 RAM 策略。
  - 管理员或权限点的 Owner 决定哪些权限点开放申请，并补充用途、数据范围和 Owner。
  - 成员在控制台或 CLI 里申请；获批后，EAT 把对应策略绑到这个人在该云账号里的个人身份（`eat-<UUID>` RAM 用户）上。
  - 成员领取自己的个人凭证（AccessKey），通过 `eat aliyun run` 把它临时注入给 `aliyun`、`ossutil` 使用。
- **数据库权限**：
  - EAT 建的库由 Owner（分配申请人）自己开放申请；外部库由管理员登记并指定 Owner。
  - 成员申请某个库的只读或读写权限；获批后，EAT 把他在该实例上的个人登录角色加入这个库的只读组或读写组。
  - 成员用 `eat db run <库> -- <命令>` 运行命令，凭证只注入子进程，不落盘。
- **OSS 身份统一**：OSS 空间的个人身份迁移到统一的身份层（同一个 `eat-<UUID>` RAM 用户、同一把 Key），以后 OSS 空间和阿里云权限共用这一个身份。
- **停用 EAT 用户**：停用后，切断他所有的个人凭证，包括阿里云 Key 和数据库个人登录角色。分配出去的 owner 账号属于资源，不动，只在页面上标出「Owner 已停用」。

## User Stories

### 阿里云：接入与目录（管理员）

1. 作为管理员，我想在系统设置里接入一个云账号，填写名称、管理 AccessKey 和可选的默认地域，这样 EAT 就能代我在这个云账号里管理 RAM 用户和策略绑定。
2. 作为管理员，我想在保存接入时让 EAT 校验管理凭证、读出它所属的云账号 ID，这样不会把凭证登记到错误的云账号。
3. 作为管理员，我想接入多个云账号，包括团队外部的云账号，每个都有自己的名称，这样一个 EAT 就能管所有云账号的权限。
4. 作为管理员，同一个云账号 ID 只能接入一次，避免两份接入互相覆盖。
5. 作为管理员，我想让 EAT 看不到管理 SK 的明文，接入详情里只显示掩码，这样管理凭证不会从页面上泄漏。
6. 作为管理员，我想暂停一个接入，让它不再接受新的申请、授予和领取凭证，同时已有授权和个人凭证照常可用。这样轮换管理凭证或排查问题时，不会把所有人都断掉。
7. 作为管理员，我想恢复一个已暂停的接入。
8. 作为管理员，我想在一个云账号里的全部授权都撤销之后删除这个接入，并让 EAT 清理它建的 RAM 用户和 Key，这样退出这个云账号时不留残余。
9. 作为管理员，删除接入时，我想让 EAT 保留 OSS 空间仍在使用的个人身份，这样在退出阿里云权限的同时，不会把成员的 OSS 空间断掉。
10. 作为管理员，我想打开目录管理时，EAT 自动刷新一次这个云账号里以 `eat-perm-` 开头的自定义策略，同时还能手动刷新，这样 RAM 里新建的策略能及时出现。
11. 作为管理员，我想看到每条策略在 RAM 里的说明。如果说明在 RAM 里改了，EAT 跟着刷新。
12. 作为管理员，我想把一个权限点开放申请，并补上用途、数据范围和 Owner，这样成员知道该不该申请，审批也有明确的负责人。
13. 作为管理员，我想关闭一个权限点的申请，已经提交的申请和已有授权都不受影响。
14. 作为管理员，如果某条策略在 RAM 里被删除了，我想看到它被标记为「云端已删除」、自动关闭申请、相关的待审批申请失效，这样目录不会指向不存在的策略。
15. 作为管理员，我想直接把任何已发现的策略授予某个成员，包括没有开放申请的，这样敏感权限只给特定的人，不必公开出来让大家申请。
16. 作为管理员，在 OSS 身份迁移完成之前，我想让 EAT 拒绝接入 OSS 所在的那个云账号，这样不会出现同一个人两个 RAM 用户的冲突。

### 阿里云：申请、审批与授权

17. 作为成员，我想在「阿里云权限」页看到每个云账号下开放了申请的权限点，包括名称、说明、用途、数据范围和 Owner，这样能找到我需要的权限。
18. 作为成员，我想对某个权限点提交申请并写明用途，这样审批人知道我拿它做什么。
19. 作为成员，同一个权限点同时只能有一条待审批申请。我重复提交时，希望被提示先撤回原来那条。
20. 作为成员，我想在统一申请中心和 `eat requests` 里看到自己阿里云申请的状态、驳回原因和执行结果，并且能撤回、重新提交。
21. 作为权限点的 Owner，我想在统一申请中心和飞书卡片上审批针对这个权限点的申请，这样审批不必经过平台管理员。
22. 作为审批人，我想在审批详情里看到申请人、用途、目标云账号、权限点说明，还能展开查看现取的策略原文，这样能核对说明和实际授予的权限是否一致。
23. 作为审批人，我想看到「已批准」和「云端已开通」是两个分开的状态，这样批准之后如果执行失败，不会被误认为驳回，可以重试。
24. 作为审批人，在接入暂停期间，我想看到「同意」按钮置灰并附有说明，而驳回照常可以做；接入恢复后，可以接着审批。
25. 作为权限点的 Owner 或管理员，我想不经申请直接把权限点授予某个成员，直接授予和批准走同一条执行路径。
26. 作为 Owner 或管理员，我给自己申请时希望直接生效，不产生一条需要自己审批自己的待办，并且记录审计。
27. 作为成员，我第一次在某个云账号获得授权时，希望 EAT 自动为我建好个人身份，不用我做任何事。
28. 作为阿里云管理员，我想在 RAM 控制台里看到 `eat-<UUID>` 用户的显示名是成员姓名、备注为 `EAT:<身份标记>:<邮箱>`，不重复用户 UUID；总长最多 128 字符，超限只截邮箱且 EAT 内保留完整邮箱，这样能认出这是谁。
29. 作为成员，如果某个云账号里已经有同名的 RAM 用户，但不是 EAT 建的，我希望开通失败，并提示交给管理员处理，而不是被 EAT 接管。
30. 作为成员，我想在「我的权限」里看到每个云账号已经绑了几条自定义策略。达到上限时，希望执行结果明确告诉我「已达到 RAM 用户自定义策略上限，请在配额中心调高」。
31. 作为成员，我想在「我的权限」里看到自己在各个云账号的全部授权，迁移过来的 OSS 空间也以只读行显示，并能跳转到对应的空间页。
32. 作为成员，我想放弃自己的某条授权，效果和撤销一样。
33. 作为 Owner 或管理员，我想撤销某个成员的授权，可以选填原因，并且 EAT 会用飞书通知他。
34. 作为管理员，如果有人在 RAM 控制台手动改了绑定，导致和 EAT 的记录不一致，我想在管理视图里看到「云端不一致」，并能手动「按 EAT 记录修复」。EAT 不会自动去覆盖。
35. 作为管理员，我想在撤销之前，EAT 先核对一次云端的实际状态。

### 阿里云：个人凭证与 CLI

36. 作为成员，我想在控制台按云账号领取自己的 AccessKey。第一次领取时创建，之后可以再次读取；响应不缓存，每次读取都记审计。
37. 作为成员，我想重置自己在某个云账号的 Key，并在重置前被告知：同一个云账号下的 OSS 空间也在用这把 Key。
38. 作为成员，我想用 `eat aliyun list` 查看开放了申请的权限点，用 `eat aliyun request <权限点> --reason …` 提交申请，用 `eat aliyun grants` 查看自己的授权，用 `eat aliyun revoke <权限点>` 放弃授权。
39. 作为成员，我想用 `eat aliyun credentials [--account <接入名称>]` 读取自己的个人凭证。
40. 作为成员或 AI Agent，我想用 `eat aliyun run [<接入名称>] -- <命令>` 运行 `aliyun` 或 `ossutil`。Key 和地域只注入子进程，父 shell 的环境和工作目录都不被修改，子进程的退出码原样透传。
41. 作为成员，如果我只在一个云账号里有授权，希望 `eat aliyun run -- <命令>` 可以不写云账号。
42. 作为成员，第一次 `run` 时如果还没有 Key，希望自动创建。新 Key 生效前，希望 stderr 提示「正在等待新 Key 生效」，而不是命令直接失败。
43. 作为成员，接入名称和云账号 ID 我都想能用，两者都能识别。

### 数据库：目录与 Owner

44. 作为 EAT 建的库的 Owner，我想把我的库开放申请，并设置覆盖哪些 schema（默认 `public`），这样同事可以申请访问，不用再找我要 owner 账号的密码。
45. 作为 Owner，我想在开放申请时让 EAT 收回这个库对 PUBLIC 的 CONNECT 权限，以及 public schema 上 PUBLIC 的 CREATE 权限，这样别人拿着其他库的个人角色也连不上我的库。
46. 作为管理员，我想在已登记的实例下登记一个外部库：填写库名、Owner、schema 列表和可选的建表角色。EAT 校验能连上，并且管理账号确实能给这个库建组角色、授予权限。
47. 作为管理员，登记外部库时，我想看到 PUBLIC 和已有角色继承下来的有效权限，以及 DBA 收紧权限要执行的 SQL。EAT 不替我改外部库。
48. 作为 Owner，我想关闭申请，已提交的申请照常可以审批，已有授权不受影响。
49. 作为成员，我想在数据库页的「数据库权限」页签里只看到开放了申请的库，包括来源（EAT 建的或外部库）、实例和 Owner。
50. 作为 Owner 或管理员，我想看到全部库，包括还没开放申请的，并能在这里直接开放。
51. 作为 Owner，我想修改 schema 列表或建表角色。修改后 EAT 自动把授权重新应用一遍。
52. 作为 Owner，用别的角色新建了表之后，我想点「重新应用授权」，把权限补到现有的全部表上。

### 数据库：申请、审批与授权

53. 作为成员，我想对某个库申请只读或读写，并写明用途。
54. 作为只读持有人，我想申请升级到读写。审批期间我照常按只读访问，批准后升级的还是同一条授权。
55. 作为读写持有人，如果我申请只读，希望被直接拒绝，并告诉我原因。
56. 作为成员，同一个库同时只能有一条待审批申请。
57. 作为库的 Owner，我想在统一申请中心和飞书卡片上审批针对我的库的申请。审批详情要显示申请人、用途、实例、库和级别。
58. 作为 Owner 或管理员，我想直接给某人授予只读或读写；对已经持有授权的人，直接授予会把级别改成新的，包括降级。
59. 作为 Owner 或管理员，我给自己申请时直接生效。
60. 作为成员，同一个实例上我在多个库都有授权时，希望共用一个个人登录角色、一套密码，而各库的权限相互独立。
61. 作为只读持有人，我能查询获批 schema 下的表和视图，写入会被拒绝。
62. 作为读写持有人，我能增、改、删获批 schema 下的数据，但不能建表、改结构，也不能 TRUNCATE。
63. 作为 Owner 或管理员，撤销某人在一个库的授权后，他在这个库上已经开着的连接会被断开，他在同一实例其他库上的授权不受影响。
64. 作为 Owner 或管理员，把某人从读写降到只读时，他在这个库上的连接也会被断开，重连后只剩只读权限。
65. 作为持有人，我想放弃自己在某个库的授权。
66. 作为持有人，我的授权被撤销时会收到飞书通知，附撤销人和原因。
67. 作为管理员，如果有人在数据库上手动改了组角色成员关系，导致和 EAT 记录不一致，我想看到「云端不一致」，并能手动修复。
68. 作为管理员，删除外部库的登记或删除实例之前，必须先撤销上面的全部授权。删除时 EAT 清理它自己建的组角色和个人登录角色；如果某个角色名下还有对象，就停下来报告，不自动删除。

### 数据库：个人凭证与 CLI

69. 作为成员，我想在控制台的授权详情里查看自己在这个实例的个人凭证。读取记审计，响应不缓存。
70. 作为成员，我想随时重置自己在某个实例的个人密码，并被告知同一实例上其他库的授权也会用上新密码。
71. 作为成员或 AI Agent，我想用 `eat db run <库>[@实例] -- <命令>` 运行命令，`DB_HOST`、`DB_PORT`、`DB_NAME`、`DB_USER`、`DB_PASSWORD` 和 `DATABASE_URL` 只注入子进程，不写 `.env`，不改父 shell，退出码原样透传。
72. 作为成员，需要管道或 shell 展开时，我显式写 `eat db run <库> -- sh -c '…'`。
73. 作为成员，同名的库分布在两个实例上时，希望 `eat db run` 报错，并给出「库名@实例名」的写法，不取任何凭证。
74. 作为成员，在没有有效授权的库上执行 `eat db run`，子进程不会启动，报错里会告诉我怎么申请。
75. 作为分配的 Owner，如果我在同一个库上同时持有授权，`eat db run` 用的是 owner 凭证。
76. 作为成员，现有的 `eat db credentials pull|run` 对我持有授权的库同样适用。
77. 作为成员，第一次 `run` 时如果还没有个人密码，EAT 自动生成并直接使用。
78. 作为成员，我想用 `eat db access list` 查看开放申请的库和自己的授权，用 `eat db access request <库> --level read|write --reason …` 提交申请，用 `eat db access revoke <库>` 放弃授权，用 `eat db access reset-password <库>` 重置个人密码。

### 停用 EAT 用户

79. 作为管理员，停用一个 EAT 用户后，他在每个云账号的全部 AccessKey 都被停用（包括有人在控制台手动给他建的 Key），策略绑定保持不变。恢复用户时，只重新启用 EAT 管理的那把 Key。
80. 作为管理员，停用一个 EAT 用户后，他在每个实例的个人登录角色改为 NOLOGIN，已有会话被断开；恢复时改回 LOGIN。
81. 作为管理员，停用一个 EAT 用户时，分配出去的 owner 账号不受影响，这样线上应用不会断。库详情上标出「Owner 已停用」，提醒我安排后续处理。
82. 作为管理员，暂停中的接入照样会执行停用用户时的切断动作。
83. 作为管理员，这些切断动作任何一步失败时，显示「同步待完成」并自动重试。
84. 作为管理员，停用用户的待审批申请会失效（沿用现有规则），停用用户不能再被授予任何权限。
85. 作为审批人，如果权限点或库的 Owner 被停用了，我在审批界面能看到「Owner 已停用」，此时由管理员审批。

### OSS 身份迁移

86. 作为管理员，我想在 OSS 设置里预演迁移，看到每个人的旧 RAM 用户名、目标 RAM 用户名、有效空间的前缀、拟迁移的授权，以及冲突项。
87. 作为管理员，我确认预演结果后执行迁移。EAT 逐人把 RAM 用户改名为 `eat-<UUID>`，AccessKey 不变，并把结果按人保存下来；中断后可以安全重试。
88. 作为成员，迁移之后我原来那把 OSS Key 照常可用，`eat oss credentials` 返回的就是我在这个云账号的个人凭证。
89. 作为成员，如果我的 OSS 空间已经全部回收，迁移时那条 `Deny oss:*` 会被解绑，这样它不会挡住我以后在这个云账号拿到的 OSS 共享权限。
90. 作为管理员，迁移完成后，回收某人最后一个 OSS 空间时，EAT 解绑他的聚合策略，而不是写入 Deny。
91. 作为管理员，迁移执行期间 OSS 的写操作返回 409。迁移完成后才能在「阿里云权限」里接入这个云账号。
92. 作为管理员，迁移之后新开通的 OSS 空间使用统一的个人身份，不再创建 OSS 专用的 RAM 用户。
93. 作为成员，迁移之后重置 OSS Key 就等于重置我在这个云账号的个人凭证，执行前会提示影响范围。
94. 作为管理员，迁移之后停用 EAT 用户，OSS 不再把他的策略切换成无授权，因为停用 Key 已经切断了访问。

### 通用

95. 作为任何人，我希望在控制台、CLI、通知和文档里看到的用词，都和 `GLOSSARY.md` 一致。
96. 作为成员，我希望个人凭证的卡片、CLI 输出和平台指南里都写明：个人凭证只给本人临时使用，不要配进线上服务。
97. 作为 AI Agent，我希望平台指南写明阿里云权限和数据库权限怎么申请、怎么用 `run`，以及「只读取数用授权，要自己存数据才申请建库」的区别。
98. 作为管理员，所有授予、撤销、放弃、读取或重置凭证、修复不一致、迁移的操作都记入审计。

## Implementation Decisions

### 统一身份层与 RAM 适配层

- **RAM 适配层（新）**：所有 RAM 调用都收进这一个深模块。阿里云权限和 OSS 共用它，两者只通过它和 RAM 交互。它提供的能力：
  - 确认调用者所属的云账号；
  - 分页读取自定义策略、读取策略原文；
  - 建 RAM 用户、改名、设置显示名和备注、删除；
  - 列出、绑定、解绑 RAM 用户的策略；
  - 列出、创建、启用、停用、删除 AccessKey。

  每次调用都由调用方传入管理凭证：OSS 用自己的管理凭证，阿里云权限用接入的管理凭证。RAM 原始错误统一转成带错误码的领域错误（比如配额已满、实体不存在、权限不足），超出配额要能和其他失败区分开。
- **统一身份层（新）**：以「云账号 ID + EAT 用户 ID」为唯一键，记录个人身份。记录的内容包括：RAM 用户名、云端 UserId、EAT 管理的 Key（信封加密，沿用 EAT_KEK）、建 Key 前的基线、待回收的 Key、Key 的世代号、用户启用状态和「同步待完成」标记。

  它对外提供以下操作，所有操作都是幂等的：
  - 确保个人身份存在；
  - 确保 Key 存在、读取 Key、重置 Key；
  - 按用户停用或启用全部 Key；
  - 确保某条策略已绑定或已解绑；
  - 核对云端实际状态与记录是否一致。

  RAM 用户名固定为 `eat-<EAT 用户 UUID 去掉连字符>`。如果云端已存在同名用户，但不是 EAT 建的，就拒绝接管并报冲突。判断是不是 EAT 建的，看 UserId 和备注。
- **Key 规则**：
  - 每个 RAM 用户最多只能有 2 把 Key。重置时先建新 Key，保存成功后再停用、删除旧 Key。如果响应丢失，按建 Key 前的基线识别孤立 Key 并回收。这套做法沿用现有 OSS 的实现。
  - 新 Key 首次使用前要等它在云端生效，等待时长可以配置，测试里调小。
- **停用 EAT 用户**：列出这个人在每个云账号的全部 Key，逐一设为 Inactive，同时删掉任何控制台登录配置（EAT 自己从不创建）。恢复时只重新启用 EAT 管理的那把 Key。策略绑定始终不动。
- **云操作的执行方式**：持久化操作表、PostgreSQL 会话级 advisory lock 串行化、云 API 调用不放在数据库事务里、后台每 30 秒检查并带失败退避、进程重启后从操作表恢复，全部沿用 OSS 现有的模式。

### 阿里云接入与权限点

- **接入**：每个接入一条记录，包含名称（`[a-z0-9-]`，CLI 用它引用接入）、云账号 ID（由接入时校验得到，唯一）、信封加密的管理 AK/SK、可选的默认地域、状态（启用 / 暂停）。
  - 只有管理员能创建、编辑、暂停、恢复和删除接入。
  - 删除前必须先撤销该接入下的全部授权。删除时清理没有被 OSS 使用的个人身份。
  - OSS 所在的云账号，要等 OSS 身份迁移完成后才允许接入。
- **权限点**：一条权限点对应接入下的一条 `eat-perm-` 自定义策略，按策略名唯一。
  - 从 RAM 同步过来的字段：策略名、说明、是否仍存在。
  - EAT 自己维护的字段：是否开放申请、用途、数据范围、Owner（可以为空）。
  - 目录刷新在管理员打开目录管理时自动触发，也可以手动触发，没有后台定时任务。
  - 策略在 RAM 里消失时，权限点标为「云端已删除」并关闭申请，相关的待审批申请失效。
  - 只认自定义策略，不认系统策略。
- **阿里云授权**：以「EAT 用户 + 权限点」为唯一键，一个人对一个权限点只有一条授权。
  - 状态：待执行、已生效、执行失败（可重试）、撤销中、已撤销。
  - 记录授予来源（审批、直接授予、给自己申请）、授予人、撤销人和撤销原因。
  - 执行顺序：确保个人身份存在 → 绑定策略。超出配额时停在「执行失败」，并给出明确的提示文案。
  - 撤销前先核对云端状态，然后解绑策略。
  - 放弃授权和撤销共用同一条执行路径，区别只是放弃不发通知。
- **谁能审批、授予和撤销**：Owner 和管理员。权限点没有 Owner 或没有开放申请时，只有管理员可以。
- **接入暂停期间**：新申请、批准和直接授予都会被拒，并带上说明；驳回和撤销照常可以做。

### 数据库权限

- **库的目录记录（新）**：以「实例 + 库名」为唯一键，来源分两种：
  - EAT 建的库：关联对应的分配，Owner 就是分配申请人；
  - 外部库：由管理员登记，并指定 Owner。

  记录的字段有：是否开放申请、schema 列表（默认 `public`）、建表角色（EAT 建的库固定为 owner 账号；外部库可以为空）、组角色名，以及对 PUBLIC 权限的检查结果。EAT 建的库的目录记录，在 Owner 第一次开放申请时创建；成员只看得到开放了申请的库。
- **组角色**：每个开放申请的库建两个 NOLOGIN 组角色，一个只读组、一个读写组。
  - 只读组：库的 CONNECT、各 schema 的 USAGE、各 schema 下全部表和视图的 SELECT。
  - 读写组：在只读组基础上，加表的 INSERT、UPDATE、DELETE，以及序列的 USAGE 和 SELECT。

  对建表角色以后新建的表，用默认权限覆盖。「重新应用授权」把以上授予在现有对象上再执行一遍，修改 schema 列表或建表角色之后也会自动执行一遍。
- **PUBLIC 权限**：EAT 建的库第一次开放申请时，收回 PUBLIC 对这个库的 CONNECT，以及 public schema 上 PUBLIC 的 CREATE，CONNECT 只授给两个组角色。owner 账号拥有这个库，不受影响。外部库只做检查和提示，并给出 DBA 要执行的 SQL，不替他修改。
- **个人登录角色**：以「实例 + EAT 用户」为唯一键，角色名为 `eat-<UUID>`（带连字符，SQL 中一律加引号），密码由平台生成、信封加密保存。
  - 第一次获得授权、或第一次读取凭证时创建。
  - 授权全部撤销后保留不删，只有删除实例时才清理。
  - 本人可以重置密码。
- **数据库授权**：以「库 + EAT 用户」为唯一键，级别分只读和读写。
  - 授权就是把个人角色加入对应的组；改级别时先加入新组、再退出旧组。
  - 撤销是退出组，并终止这个角色在这个库上的全部会话。降级时同样要终止会话。
  - 状态机与阿里云授权相同：待执行、已生效、执行失败、撤销中、已撤销。
- **申请规则**：
  - 同一个人对同一个库只能有一条待审批申请；
  - 读写持有人申请只读，直接拒绝；
  - 只读持有人申请读写，审批期间照常按只读访问；
  - Owner 或管理员给自己申请，按直接授予处理；
  - 直接授予可以修改已有授权的级别，包括降级。
- **只支持 PostgreSQL**：MySQL 实例上的库，不能开放申请，也不能登记为外部库。
- **删除**：删除外部库的登记或删除实例之前，必须先撤销上面的全部授权。删除时，EAT 删掉自己建的组角色和个人登录角色；如果某个角色名下还有对象，就停下来报告，不执行 `DROP OWNED`。这是决策 13 的例外：决策 13 只针对分配出去的 owner 账号和库本身，库永远不删。
- **管理账号的能力要求**：实例的管理账号需要 CREATEROLE，并且能授予目标表上的权限。EAT 建的库，由管理账号借 owner 账号的成员身份完成授予。校验不通过时，报错里给出需要执行的 SQL。

### 统一申请中心

- **新增类型**：申请类型新增 `db-access`（数据库权限）和 `aliyun`（阿里云权限）。需要同步扩展的地方有：类型枚举和中文名称、Owner 的计算（新类型按库或权限点的 Owner）、失效规则（资源被删除、关闭申请不导致失效、策略在云端被删除、用户停用）、执行状态的展示，以及按类型展示的审批详情。
- **通知与卡片**：
  - 复用持久化通知队列、飞书审批卡片和快捷同意。
  - 卡片上显示云账号或库、权限点或级别，以及用途。
  - 快捷同意走统一的执行路径；接入暂停期间，快捷同意会被拒绝，并附上说明。
- **现有入口同步**：`eat requests list --type` 和 MCP 的 `list_requests` / `get_request_status` 的类型枚举，都要加上这两个新类型。
- **撤销通知**：通过通知服务发给持有人，内容包括撤销人和原因。放弃授权不发通知。

### OSS 改造与迁移

- **职责划分**：个人身份和 Key 改由统一身份层负责。OSS 只保留空间、审批、聚合策略的内容与绑定（通过 RAM 适配层），以及 Bucket 公开读。OSS 原有的账号记录改为引用统一身份记录。
- **空策略与用户停用**：用户名下一个有效空间都没有时，解绑聚合策略，不再写入 `Deny oss:*`；聚合策略本身保留。停用用户时，只走统一身份层的停用 Key，不再切换策略。
- **凭证命令**：`eat oss credentials` 读取统一身份层里的 Key；`reset` 就是重置这个云账号的个人凭证，执行前提示影响范围。
- **迁移**：OSS 设置里增加迁移的状态、预演、执行三项。
  - 预演会逐人列出：旧 RAM 用户名、目标 RAM 用户名、有效空间的前缀与操作、拟迁移的授权，以及冲突项（目标用户名已被非 EAT 建的用户占用等）。
  - 执行时逐人进行：改名为 `eat-<UUID>`（AccessKey 不变）→ 写入统一身份记录 → OSS 记录改为指向它 → 空间已全部回收的用户解绑 Deny 策略。每个人的结果持久化，可以安全重试。
  - 执行期间，OSS 的写操作返回 409。
  - 迁移完成之前，旧路径照常工作；旧路径代码在后续版本中删除。
- **生产环境**：不在生产环境执行迁移，代码只提供能力。

### EAT 用户停用与恢复

- 现有的停用与恢复处理里，新增两个钩子：统一身份层的「按用户停用或启用全部 Key」，以及数据库个人登录角色的 NOLOGIN / LOGIN（停用时同时终止会话）。失败时标记「同步待完成」并自动重试。接入处于暂停状态时，这两个钩子照常执行。
- 分配出去的 owner 账号不动。分配详情和清单上，按 Owner 的状态显示「Owner 已停用」。

### CLI

- **数据库**：
  - `eat db run <库>[@实例] -- <命令>` 是 `eat db credentials run` 的简写，按名字解析时同时匹配分配和授权，同一个库都命中时优先用 owner 凭证。
  - `eat db credentials pull|run` 扩展为也支持授权。
  - 新增 `eat db access list | request | revoke | reset-password`。
- **阿里云**：新增 `eat aliyun list | request | grants | revoke | credentials [reset] | run`。`run` 注入的环境变量是 `aliyun` CLI 和 `ossutil` 读取的标准变量名，加上地域；具体变量名在实现前对照官方文档确认。
- **共同约定**：
  - 第一次 `run` 时自动创建个人凭证，等待新 Key 生效期间在 stderr 提示。
  - 凭证只注入子进程，退出码原样透传。
  - 名字有歧义、或没有有效授权时，不取凭证、不启动子进程。
- **只在控制台的管理操作**：审批、直接授予、撤销他人的授权、开放或关闭申请、接入、外部库登记、修复不一致，都不提供 CLI。
- **版本号**：递增 CLI 的 minor 版本，同步 `package.json`。平台指南内容变了，递增指南版本。

### 控制台

- **系统设置 → 阿里云接入**：
  - 每个接入可以新建、编辑、校验、暂停、恢复和删除。
  - 在 OSS 迁移完成之前，接入 OSS 所在的云账号会被拒绝，并提示先去完成迁移。
- **「阿里云权限」页**：至少有一个接入时，导航里才出现这个页面。
  - 页签「目录」：按云账号分组，显示开放申请的权限点。
  - 页签「我的权限」：每个云账号下的授权、已绑定的策略数、凭证卡片，以及迁移过来的 OSS 空间（只读行）。
  - 页签「管理」：仅 Owner 和管理员可见。包括发现到的策略、开放申请、Owner、直接授予、授权清单、撤销，以及「云端不一致」的修复。
- **数据库页**：新增「数据库权限」页签，包括开放申请的库、我的授权、凭证、申请入口；Owner 和管理员还有管理视图。外部库的登记入口在实例下面。分配上显示「Owner 已停用」标记。
- **OSS 设置**：增加迁移的状态、预演和执行。
- **统一申请中心**：增加这两类申请的筛选和审批详情。
- **表单与组件**：沿用现有组件层的约定：表单用 zod 契约、悬停提示用 `Tip`、表格用 `DataTable`。

### 契约与数据

- **schema 契约**：所有新接口的入参和出参都用 shared 里的 zod 契约，三端共用。按名字解析库或接入的逻辑放在 shared，CLI 和服务端共用一份。
- **新增表**：阿里云接入、个人身份（云账号）、权限点、阿里云授权、库的目录记录、个人登录角色（实例）、数据库授权，以及 OSS 迁移结果。
- **改造的表**：OSS 账号记录改为引用个人身份，OSS 设置增加迁移状态。
- **迁移原则**：存量数据原地搬迁，不删历史。

## Testing Decisions

- **什么是好的测试**：只从外部能观察到的行为去断言，不断言 SQL 怎么拼、调用了哪个内部方法。
  - 数据库这边：用个人凭证真连上去，看查询或写入实际是成功还是被拒。
  - 阿里云这边：看内存实现里模拟的云端状态（绑了哪些策略、Key 是否 Active），以及接口的返回。
- **切入点 1：服务端 HTTP 接口（主切入点）**：起完整的应用，通过注入请求走真实接口，覆盖全部业务规则。前例是现有的 server e2e：真实建库的数据库用例、OSS 用例、统一申请中心用例。
  - 数据库部分不打桩：本地 PostgreSQL 16 同时当 EAT 自己的库和被授权的目标实例。必须覆盖：
    - 同一实例两个库，同一个人只有一个个人角色，每个库各一条授权；
    - 只读能查、不能写；
    - 读写能改获批 schema 下的表；
    - 升级仍是同一条授权；
    - 撤销 A 库之后 B 库照常可用，A 库已开着的会话被断开；
    - 重复审批和失败重试复用同一个角色和同一条授权；
    - 收回 PUBLIC CONNECT 之后，别的库的个人角色连不上；
    - 用户停用后 NOLOGIN，恢复后能登录；
    - 删除时角色名下有对象，就停下来报告。
  - 阿里云部分只替换 RAM 适配层这一个边界，用内存实现。必须覆盖：
    - 同一个人在同一个云账号多次开通，复用同一个身份；
    - 撤销只解绑对应的那条策略；
    - 云端失败时显示失败，并可以重试；
    - 超出配额时报出明确的错误；
    - 暂停接入的行为；
    - 策略在云端被删除时，申请失效；
    - 云端不一致的检测与修复；
    - 停用用户后 Key 变为 Inactive，恢复后只启用 EAT 管理的那把；
    - 同名的非 EAT 用户报冲突。
  - OSS 迁移：用现有的 OSS 流程造出旧身份，然后预演、执行、重试。必须覆盖：
    - 改名后 Key 不变；
    - Deny 策略被解绑；
    - 迁移后新空间使用统一身份；
    - 迁移前拒绝接入 OSS 所在的云账号。
  - 统一申请中心：新类型的 Owner 审批、飞书快捷同意、失效规则、「已批准」与「云端已开通」分开显示。
- **切入点 2：RAM 适配层（唯一新增的边界）**：现有 OSS 测试的内存实现里模拟 RAM 用户的部分，挪进 RAM 适配层的内存实现，OSS 用例改用它。这个内存实现必须照真实云的规则来：
  - 每个 RAM 用户最多 2 把 Key；
  - 每个 RAM 用户最多绑 10 条自定义策略；
  - 改名后 Key 不变；
  - 删除策略前必须先解绑；
  - 删除 RAM 用户前必须先清掉它的 Key 和策略绑定。
- **切入点 3：CLI 命令函数**：前例是现有 CLI 的数据库凭证测试，把 API 客户端换成桩，直接调用命令函数，子进程是真实启动的。必须覆盖：
  - 名字解析（`库@实例`、接入名称或云账号 ID）以及歧义时的报错；
  - 子进程能读到注入的变量，父进程的环境不被修改，不写任何文件，退出码原样透传；
  - 没有授权时子进程不启动；
  - 第一次运行时自动创建凭证，并在 stderr 打出等待提示。
- **切入点 4：真实阿里云契约测试**：单独的脚本，要显式设置环境变量才会运行，不进 `pnpm test`。
  - 只测 RAM 适配层本身，用的是本机的阿里云凭证。
  - 验证项：建用户、改名后旧 Key 仍能调用、绑满 10 条策略时的错误码、新 Key 生效的延迟、清理之后没有残留。
  - 资源全部用本轮新生成的 UUID 和专用的测试前缀；适配层里加白名单，不在白名单里的资源一律不允许改名、解绑或删除。
  - OSS 迁移的演练使用临时建的 Bucket，测完删掉。
- **控制台**：沿用现有的 Playwright 冒烟脚本，在桌面和手机两种宽度下走查新页面、新页签和弹窗。

## Out of Scope

- MCP 工具：本期不新增数据库权限和阿里云权限相关的 MCP 工具，只在 `list_requests` / `get_request_status` 的类型枚举里加上两个新类型。
- MySQL 的数据库权限，以及 MySQL 自动建库。
- 按表勾选的授权粒度（本期按 schema）、DDL 权限、库所有权。
- 授权有效期和自动到期。
- 每个库单独一套个人密码。
- 系统策略直接作为权限点；一个权限点打包多条策略。
- 自动修复云端不一致。
- 分配的 Owner 转交、owner 账号的密码轮换。
- 多个真实云账号的联调：只有一个真实云账号可用，多接入的逻辑靠内存实现覆盖。
- 生产环境的 OSS 身份迁移执行、部署，以及删除旧 OSS 身份路径的代码。

## Further Notes

- **真实云账号是线上在用的账号**：里面有线上 EAT 的 OSS 实例和真实成员的 RAM 身份，以及与 EAT 无关的业务资源。真实云测试只能操作本轮新建的资源，不能碰任何已有的 `eat-oss-*` 身份。测试结束后，不能留下任何 `eat-perm-*` 策略，否则功能上线后会被线上 EAT 当成目录里的权限点发现。
- **RAM 配额**：实测这个云账号的值是：每个 RAM 用户最多 2 把 AccessKey（不可调）、最多绑 10 条自定义策略（可调）、最多加入 10 个用户组。所以在 OSS 所在的云账号里，每人最多持有 9 个权限点。
- **RAM 没有「停用用户」的接口**：RAM 和 IMS 的 API 都没有用户级的启用或停用开关。停用个人身份的实际做法就是停用它的全部 Key。
- **PostgreSQL 版本差异**：PG 15 起 public schema 的 owner 是 `pg_database_owner`，并且 PUBLIC 默认没有 CREATE 权限；PG 14 及更早，PUBLIC 有 CREATE。CONNECT 无论哪个版本，默认都授给 PUBLIC。
- **和历史决策的关系**：
  - 决策 81（统一权限申请中心）规定数据库和 OSS 类申请只能由管理员审批。本规格的两个新类型改成 Owner 和管理员都可以审批。
  - 决策 13 不删库、不删账号。本规格对 EAT 自己建的权限角色开了一个例外。
- **相关 ADR**（`docs/adr/`）：
  - 0001：统一身份层由 OSS 和阿里云权限共用，OSS 身份改名迁入；
  - 0002：每人在每个 PostgreSQL 实例上只有一个个人登录角色；
  - 0003：停用 EAT 用户只切断个人凭证，不动分配出去的 owner 账号；
  - 0004：EAT 自己清理为数据库权限建的角色。
- **文档**：新增数据库权限和阿里云权限两份功能文档，更新 OSS 存储文档、`docs/features.md` 和 README 的能力矩阵，以及平台指南。

### 2026-11-09 已批准的 RAM 用户备注规则（以下按最后一次用户指令执行）

- 阿里云 RAM 2015-05-01 的 CreateUser/UpdateUser 官方 SDK 与文档均限制 comments 为 1–128 字符；平台当前允许的邮箱可超过备注可用空间，原「备注含完整 EAT 用户 ID 和邮箱」无法在所有输入下成立。
- 用户最新明确指令：**备注格式为 `EAT:<身份标记>:<邮箱>`，去掉重复的 EAT 用户 ID。保留完整身份归属标记；仅当邮箱超出剩余空间时截断邮箱并加省略号；EAT 内保留完整邮箱。** 普通邮箱在空间足够时保持完整，不因长邮箱拒绝授权。该最新格式覆盖此前“备注同时保留完整用户 ID”的批准。
