# LLM API 网关原生额度配置说明

## 一期决策

一期直接使用 New API 现有的 Key 配置和启停接口，接受保存期间并发扣费可能被余额覆盖所产生的额度偏差。配置完成后即可申请、启用和调额，不设置发布阻断或额外预览开关，也不要求修改 New API 或增加原子接口。

验证基于 New API `v1.0.0-rc.36`（提交 `ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b`）的源码与实际接入。真实实例已验证创建、模型调用扣费、停用拒绝新请求、恢复和原生调额，测试 Key 已清理。

## 可复现的余额覆盖

[`controller.UpdateToken`](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/controller/token.go#L383) 读取 Key；`status_only` 只改变内存对象的状态，但之后仍调用 [`Token.Update`](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/model/token.go#L310)，SQL 的列集合包含 `remain_quota`，不包含 `used_quota`。模型扣费则通过增量更新同时减少剩余、增加已用。两条写入之间没有共用的原子操作边界。

| 时序 | 剩余 | 已用 | 说明 |
|---|---:|---:|---|
| 初始 | 100 | 0 | 总额度 100 |
| 管理端读取 | 100 | 0 | 准备增加 50，目标剩余 150 |
| 模型结算扣 7 | 93 | 7 | 原总额度仍为 100 |
| 配置写入 150 | 150 | 7 | 总额度变成 157，应为 150 |

仅停用也存在同样的反例：New API 内部读取剩余 100 → 在途请求扣 7 → `status_only` 将旧剩余 100 写回，最终已用 7、剩余 100。EAT 侧再加锁、先读一次、先停用再等待一个固定时长，均不能覆盖 New API 内部和在途结算的全部执行窗口。

`apps/server/test/newapi-consistency.spec.ts` 保留上述已接受行为的源码语义复现测试；业务测试另外验证生产环境可直接申请、调额和启停。EAT 的用户锁与持久化操作标识仍用于避免重复申请和重复调额，不改变 New API 的并发写入语义。

## 在途请求与删除

停用只阻止后续鉴权；已接收请求仍可能扣费或退款。物理删除会使后续按 Key ID 更新失去可查询对象。因此 EAT 的删除先停用，再将绑定标记为历史；保留停用的上游 Key，后台核对历史消耗，并在新 Key 分配中扣除。此策略保存结算归属，不解决上游配置接口的余额覆盖问题。
