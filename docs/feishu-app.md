# 飞书自建应用通知

EAT 的个人通知有两种渠道，由管理员在「系统设置 → 飞书通知」里二选一（决策 92）：

| 渠道 | 成员要做的 | 卡片能做的 |
|---|---|---|
| 个人飞书群机器人（Webhook） | 自建一个只有自己的群，添加自定义机器人，粘贴 Webhook 地址并通过验证码验证 | 按钮只能跳转网页 |
| 飞书自建应用机器人 | 在个人中心的通知设置中点击绑定，复制弹窗内验证码并私聊发给机器人 | 审批卡片直接点「同意 / 驳回」，处理后卡片原地更新为结果 |

两种渠道的成员数据分开保存，切换渠道不会清掉另一边已完成的配置，随时可以切回。

## 管理员：安装应用

飞书没有像 GitHub App Manifest 那样「带着权限一键创建企业自建应用」的公开接口，所以安装分两半：在飞书开发者后台创建应用并导入权限，在 EAT 填凭据并检查。设置页的「安装指引」里有同样的步骤和可复制的值。

1. 打开 [飞书开发者后台](https://open.feishu.cn/app)，「创建企业自建应用」（名称建议「EAT 通知」），在「添加应用能力」里添加**机器人**。
2. 「权限管理 → 批量导入/导出权限」，粘贴设置页给出的 JSON：

   ```json
   { "scopes": { "tenant": ["im:message:send_as_bot", "im:message.p2p_msg:readonly"], "user": [] } }
   ```

   | 权限 | 用途 |
   |---|---|
   | `im:message:send_as_bot` 以应用的身份发消息 | 私聊推送通知卡片、回复绑定结果、更新审批卡片 |
   | `im:message.p2p_msg:readonly` 读取用户发给机器人的单聊消息 | 接收成员私聊发来的绑定码 |

3. 复制「凭证与基础信息」里的 App ID、App Secret，「事件与回调 → 加密策略」里的 Verification Token 与 Encrypt Key（为空时点「重置」生成），填到 EAT 并保存。**Encrypt Key 必填**：审批是通过卡片回调执行的，EAT 只接受签了名的回调。
4. 回到「事件与回调」：「事件配置」和「回调配置」的订阅方式都选「发送至开发者服务器」，请求地址都填设置页显示的 `<EAT_PUBLIC_URL>/api/feishu/callback`；事件添加「接收消息 `im.message.receive_v1`」，回调添加「卡片回传交互 `card.action.trigger`」。保存地址时飞书发起验证，EAT 自动应答，设置页的「请求地址」一项随之变绿。
5. 「版本管理与发布」创建版本，可用范围选需要接收通知的成员（建议全员），提交发布，等企业管理员审核通过。
6. 回到 EAT 点「检查状态」。全部通过后，在「通知渠道」里切换为自建应用。

`EAT_PUBLIC_URL` 必须是飞书能访问到的公网 HTTPS 地址，否则第 4 步的地址验证过不去。

### 检查状态与申请权限

「检查状态」依次核对：App ID / Secret 能换到 tenant_access_token → 机器人能力已开启并启用（`bot/v3/info`）→ 两项权限在本企业的授权状态（`application/v6/scopes`）→ 请求地址收到过通过验签的推送。打开设置页时会静默检查一次。

权限有三种状态：

- **已开通**：可以用。
- **待管理员审核**：已在开发者后台添加，但企业管理员还没批。点「申请权限」由 EAT 以应用身份调用飞书接口向企业管理员发起申请（同一版本最多 10 次）。
- **未添加**：开发者后台还没勾。「申请权限」会打开开发者后台的权限页并预选好缺的权限，勾选后要「创建版本并发布」才生效。

这两个动作用的都是飞书开放平台的公开接口，文档标明调用无需额外权限：[查询租户授权状态](https://open.feishu.cn/document/application-v6/scope/list.md)（`GET /open-apis/application/v6/scopes`）与 [向管理员申请授权](https://open.feishu.cn/document/application-v6/scope/apply.md)（`POST /open-apis/application/v6/scopes/apply`）。申请接口只能申请**已添加到应用**的权限，不能替应用新增权限，所以「未添加」的仍要在开发者后台勾选并发布版本（EAT 给的是开发者后台权限页的链接，不是接口调用）。

文档列出的错误会显示成中文提示：

| 错误码 | 含义 | 怎么办 |
|---|---|---|
| 212001 | 剩余未授权的都是高敏权限 | 在开发者后台提交，或请企业管理员在管理后台审批 |
| 212002 | 没有可申请的权限 | 可能已全部授权，点「检查状态」刷新 |
| 212003 | 同一版本申请超过 10 次 | 直接联系企业管理员，或发布新版本后再申请 |
| 212004 | 重复申请 | 已在等待企业管理员审批 |
| 212100 | 应用未在企业内安装 | 发布版本并等待审核通过 |

权限状态查询失败时不单独阻断切换，设置页给出原因，请人工核对。

EAT 不使用飞书未公开的接口：像 lark-cli / OpenClaw 那样「扫码自动创建应用」靠的是没有公开文档的注册接口（只能建「个人智能体」原型、不能指定权限），因此这里仍由管理员在开发者后台创建应用。

### 切换渠道

只有检查全部通过才能切换到自建应用；切回 Webhook 不受限制。切换前确认弹窗会给出已绑定人数。如果开启了「注册与登录 → 强制配置飞书通知」，切换后还没绑定的成员下次访问会被引导到完善资料页完成绑定。

使用自建应用渠道时不能直接更换 App ID（会让所有人的绑定失效），需要先切回 Webhook。更换应用后成员要重新绑定，用户列表里显示为「需重新绑定」。

## 成员：绑定飞书账号

进入「个人中心 → 通知设置」，点击「绑定飞书机器人」区域的「绑定」按钮打开弹窗；进入页面时不会自动生成或显示验证码。弹窗内按顺序完成两步：

1. 点击第一步下方的机器人卡片，在飞书里打开对话。
2. 复制第二步下方的验证码（形如 `EAT-7KQ2MX`），原样发送给机器人。

弹窗打开且验证码有效时每 3 秒检查绑定状态；成功后自动关闭弹窗，通知设置显示「已绑定」。关闭弹窗会停止轮询，再次打开可以继续使用尚未过期的验证码。已绑定时提供「解绑」和「重新绑定」；重新绑定成功前保留原绑定，取消操作不会解绑。强制完善资料页面也使用同一绑定弹窗。

- 绑定码 10 分钟有效，过期或重新生成后旧码作废；平台只存哈希。
- 一个飞书账号只对应一个 EAT 账号。用同一个飞书账号去绑另一个 EAT 账号，视为本人把通知转过去，旧绑定自动解除。
- 同一个飞书账号 10 分钟内绑定码错 10 次后暂停尝试。
- 绑定后可以「发送测试通知」确认链路可用，也可以随时解除绑定。

管理员在用户列表的「飞书通知」列能看到每个人的状态（已绑定 / 未绑定 / 需重新绑定；Webhook 渠道下是是否验证过）。

## 审批卡片

自建应用渠道下，审批人收到的待审批卡片带「同意」「驳回」「查看详情」：

- **同意**：直接执行，卡片原地变为「已批准」并写明审批人与时间。环境变量申请照旧不设到期时间，需要限制有效期请查看详情。
- **驳回**：卡片先展开原因输入框（必填，申请人会看到），提交后变为「已驳回」。
- 身份按「点按钮的人绑定的 EAT 账号」认定，且卡片必须是发给这个人的那一张；权限、申请状态照常实时复核。转发出去的卡片点了不生效。
- 资源开通较慢（例如数据库建库）超过飞书回调的 3 秒时限时，卡片先显示「正在处理」，完成后自动更新。
- 同一个申请发给了多位审批人：任何一处（卡片、网页、申请人撤回、申请失效）处理后，所有人手里的卡片都会在 30 秒内更新为最终状态。

求助、回复、Folio 评论提及、GitHub 操作告警等其他通知，内容与 Webhook 渠道相同，改由机器人私聊发送。

## 排查

| 现象 | 看哪里 |
|---|---|
| 「请求地址」一直未验证 | 开发者后台保存地址时是否报错；`EAT_PUBLIC_URL` 是否公网可达；Encrypt Key / Verification Token 是否与 EAT 一致（改过要重新保存） |
| 回调返回 400「请配置 Encrypt Key」 | 开发者后台「加密策略」没设 Encrypt Key |
| 回调返回 401 | 签名或 Verification Token 不一致；在 EAT 重新填写后再在开发者后台保存一次地址 |
| 发给机器人绑定码没反应 | 事件配置是否添加了 `im.message.receive_v1`；权限 `im:message.p2p_msg:readonly` 是否已开通；版本是否已发布 |
| 卡片按钮点了提示失败 | 回调配置是否添加了 `card.action.trigger` |
| 通知投递失败（`230013` 等） | 成员不在应用的可用范围内，调整可用范围后重新发布 |

投递记录在 `webhook_delivery` 表（自建应用渠道的目标记为 `feishu-app:<App ID>:<open_id>`），审批通知的失败原因显示在申请详情上。
